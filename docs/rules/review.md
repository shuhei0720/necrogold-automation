# 独立レビュー

2026-11-10の最新ユーザー指示に従い、通常修正は独立した差分レビュー1回を基本とする。1担当が以下3観点を確認し、毎回3担当/複数周を要求しない。指摘の修正確認は必要な差分へ限定する。大きな入力権限/取消/期限の契約変更、並行処理の構造変更、広いAPI/ABI変更では作成経緯を渡さない設計・網羅・安全の重点レビューを行う。既存契約内の局所修正を形式的に大変更としない。

- 設計: 要件とプランの矛盾、SSOT、責務と実現性。
- テスト: 正常・境界・異常、未観測を正解にしたケース、データ漏洩、モックと実機の区別。
- セキュリティ・運用: 秘密値、入力先の誤認、キャンセル、無期限待機、配布状態。

P0は必須修正、P1は重要な不足、P2は軽微。各指摘にファイル位置・根拠・壊れる例を付ける。重点レビューの修正・再レビューは最大3周。P0がある状態は実装着手・マージ不可。P1を残す場合は合理的理由と担当する工程を記録し合格と黙って扱わない。

レビュー結果は `docs/reviews/` に保存する。静的レビューではiPhoneの動作を証明できない。今後のPRでは最新commitの必須CIと対応する実機結果を確認し人間がレビューする。未構築のCIを構築済みと書かない。

時間を短くするために品質基準を緩めない。固定時間ノルマは置かない。検査/レビュー範囲の選択と根拠、未実施、再利用する過去結果を明示し、静的/模擬/実機の証明範囲を混同しない。

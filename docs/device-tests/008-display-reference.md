# TEST-008: 通常スクリーンショットで表示形状の基準を確認

状態: **資料待ち・未実施**。2026-11-05（日本時間）。コード変更・診断コマンドの再実行は不要。

## 1. 概要

TEST-006/007で画像取得が成立し、TEST-007では既存native_i386の利用と復号時間の短縮を確認した。次は、取得画像の縦長の見え方を、iPhone標準のスクリーンショット1枚と比較する。

## 2. 背景

TEST-007の原画像は414×896または828×1792、EXIF orientation=1、報告point寸法414×896。保存3枚はGAME PAUSEだが、メニューが縦長に見える。P1.4は画像を伸縮・回転せず原バイトを保存する。取得元より前のどこで形状が変わったか、入力ptがどの向きかは未確認。

過去動画の縮尺や旧R12の補正値からタップ位置を推測しない。通常スクリーンショットとの形状比較も、入力座標の検証を代替しない。

## 3. 比較設計

同じiPhone、ゲーム、GAME PAUSE、左側が下の向きを維持する。診断ツールを起動せず、端末標準のスクリーンショット機能で画面を1枚保存し、元ファイルを受領する。TEST-007の保存原画像との寸法、EXIF、文字や枠の相対位置・縦横比を照合する。

別時刻・別取得経路の画像なので完全同時フレームとは扱わない。手動画像の受領だけで取得APIの鮮度、px→入力ptの対応、歪みの根本原因を確定しない。

## 4. 影響範囲

ゲームの既存ポーズを維持する。続行やオプション操作、位置情報読取りの追加、プログラム変更は行わない。前回の終了画面を保存したら、iSHはアプリスイッチャーから終了し、継続用読取りを終えておく。

## 5. 判定条件

| 受領内容 | 判定・次の対応 |
| --- | --- |
| 同じポーズの未加工原画像 | 寸法・EXIF・枠/文字配置を比較し、取得経路間の違いを記録。必要な補正の仮説を作る |
| 標準画像は横長、API画像は縦長 | 取得経路間に形状差あり。単純な90度回転か軸ごとの伸縮かを画像配置から区別する。入力座標は別途検証 |
| 標準画像も同様の縦長 | 表示/向き/端末取得の条件を再確認。画面内容を勝手に伸ばして正解にしない |
| 切抜き・回転・縮小済み、別画面、向き不明 | 幾何比較に使えない範囲を記録。推定座標を採用しない |

## 6. 実施手順

1. 前回の記録を残してiSHを終了する。
2. ゲームの同じGAME PAUSE画面を、いつもの「左側が下」の横持ちで表示する。
3. iPhone標準のスクリーンショットを1枚撮る。
4. 切抜き・回転・サイズ変更をせず、その画像を送る。通知等に秘密情報が写った場合は、その画像を共有せず表示が消えてから撮り直す。

撮影のためにゲームを再開したりオプションへ入ったりする必要はない。新しいシェルコマンドはない。

## 7. 確認と工程

現在の原report・保存画像・P1.4の原バイト保存コードを根拠に、次の資料条件を定義した。[TEST-007分析レビュー](../reviews/p1-test007-analysis.md)で設計・証拠・安全性を独立確認する。資料の未受領を合格扱いしない。資料受領後、入力を伴わない幾何の検証計画を具体化する。コード変更が必要なら別プラン、実装前Red→Green、独立実装レビューを行う。

## 8. スコープ外

自動タップ、入力座標の合格判定、鮮度/取消の合格判定、ゲーム続行E2E、自動周回、恒久的な背景継続、長時間試験、速度目標の緩和。今回の原画像1枚は形状の比較資料であり、P1全体の合格証拠ではない。

**この組合せの違いは単純な90度回転ではなく、縦横別々の倍率による形状差で説明できる。** タイトル、続行、GAME CENTER、ランキング、オプション、カスタムミュージック、クイックリスタート、ロビーの並びが同方向で、画面寸法に対する相対位置も対応する。

JPEG scale2の8文字領域について、白い画素の外接矩形を幅/高さで正規化すると、通常画像との差は全32辺の最大でも0.000946234（画面幅/高さに対して約0.095%）。scale1では同じ閾値で抽出した境界の最大差は0.007057669。これらは当該ポーズ画面の比較値で、認識精度やタップ誤差ではない。

画像の表示形状だけを通常画像の寸法に合わせる計算では、414×896→1792×828は横4.328502倍・縦0.924107倍、828×1792→1792×828は横2.164251倍・縦0.462054倍となる。**これは画像同士の比較倍率であり、入力ptへの変換式ではない。** 再拡大しても失われた細部を復元できるとは限らない。

### 公開コードと照合した原因候補

LoopCtrlの公開commit [`6fc759fcce397c92482c2a8c6f90244e5374aac9`](https://github.com/Souitou-iop/LoopCtrl/blob/6fc759fcce397c92482c2a8c6f90244e5374aac9/LoopCtrlUITests/ActionHandler.swift)では、`pointSize`が`app.frame`をキャッシュし、`screenshot`がその寸法×scaleを出力サイズに使い、`resize`が画像をその矩形へ描画する（315〜341、1710〜1788、1846〜1862行）。縦の寸法キャッシュに横向き画像を描くと今回のような変形を生む、という仮説と整合する。

ただしP1.4のreportには取得元のserver_version/buildが残らず、実機バイナリとこの公開commitの一致は未確認。キャッシュ値の変化も未観測なので、**原因確定・上流修正済みとは扱わない**。P1.4側は原バイトを保存しており、少なくとも受領したAPI原画像に既に形状差が含まれる。

入力座標、画像生成時刻/鮮度、端末側取消は未検証。通常画像のアップロードや今回の相関値をタップの許可に変えない。次は[画像幾何と入力契約を分離する改修計画](../plans/p1-geometry-validation.md)へ進む。今回は追加の端末操作やTEST-008の撮り直しは不要。[独立レビュー](../reviews/p1-test008-analysis.md)参照。

## 1. 概要

TEST-006/007で画像取得が成立し、TEST-007では既存native_i386の利用と復号時間の短縮を確認した。次は、取得画像の縦長の見え方を、iPhone標準のスクリーンショット1枚と比較する。

## 2. 背景

TEST-007の原画像は414×896または828×1792、EXIF orientation=1、報告point寸法414×896。保存3枚はGAME PAUSEだが、メニューが縦長に見える。P1.4は画像を伸縮・回転せず原バイトを保存する。取得元より前のどこで形状が変わったか、入力ptがどの向きかは未確認。

過去動画の縮尺や旧R12の補正値からタップ位置を推測しない。通常スクリーンショットとの形状比較も、入力座標の検証を代替しない。

## 3. 比較設計

同じiPhone、ゲーム、GAME PAUSE、左側が下の向きを維持する。診断ツールを起動せず、端末標準のスクリーンショット機能で画面を1枚保存し、元ファイルを受領する。TEST-007の保存原画像との寸法、EXIF、文字や枠の相対位置・縦横比を照合する。

別時刻・別取得経路の画像なので完全同時フレームとは扱わない。手動画像の受領だけで取得APIの鮮度、px→入力ptの対応、歪みの根本原因を確定しない。

## 4. 影響範囲

ゲームの既存ポーズを維持する。続行やオプション操作、位置情報読取りの追加、プログラム変更は行わない。前回の終了画面を保存したら、iSHはアプリスイッチャーから終了し、継続用読取りを終えておく。

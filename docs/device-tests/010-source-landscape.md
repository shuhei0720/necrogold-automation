# TEST-010: 取得元から横長の原画像を受け取る

状態: **実施・結果確認済み（横長原画像の取得は合格、P1全体は未合格）**。2026-11-05 21:27:52開始（日本時間、run名による）。P1.5のreport・原画像3枚・終了画面を受領。12/12正常終了、保存3枚とも正常な比率のゲームポーズを確認した。以下の導入手順は今回実施した手順の記録。再インストール・同じ試験のやり直しは不要。

## 何を直したか

LoopCtrlの出力用描画が古い入力側寸法414×896を使っていた箇所を、新モードではUIImage自身の形状から計算する。既存の出力用描画・符号化1回を使い、iSH受信後の回転・縦横リサイズ・再符号化は追加しない。既存の内部小型フレーム生成は残る。新モードではそこで失敗しても追加キャプチャをしない。

診断クライアントは最初のdevice_infoで新capabilityを必須確認する。未対応・照会失敗ならゲーム起動/画像取得前に停止する。応答のgeometry、形状、実JPEG/PNGの寸法、出力EXIFを照合し、旧方式への自動フォールバックは行わない。出力原画像はバイト列のまま保存する。

## 1. LoopCtrlを更新する

今回の `LoopCtrl.ipa` を「ファイル」に保存し、SideStoreの **My Apps → ＋** からそのIPAを選択する。既存LoopCtrlへの更新として取り込む。既存アプリの削除は不要。上流の署名案内は[固定v0.3.4 README](https://github.com/Souitou-iop/LoopCtrl/blob/6e25cf6a9f65bc86c372cdce94bdb151d0cf6767/README.md#install)。`.xctest`の署名に対応したSideStoreが必要で、現在LoopCtrlを導入できた方法を使う。

IPAはユーザー証明書では署名していない配布用（ad-hoc署名）で、SideStoreが再署名する。アプリ表示版は0.3.4のまま、API版は1.98.14-ngg1。build-manifestとIPA SHA-256は[記録](../validation/ngg1-build-manifest.json)を参照。保存済みの設定やペアリングを削除する操作は含めない。

更新したLoopCtrlを開き、いつものVPN/ディスクイメージ接続を確認して **Start Server**。再起動した場合は上流手順どおりDisk Imageを再マウントする。承認画面が出た場合は端末上で確認する。

## 2. P1.5を展開・マウントする

`necro_p15.zip`を「ファイル」で展開する。旧版とは別の`necro_p15`フォルダを使う。`start_probe.sh`と`test_010.sh`が直下にあるフォルダをマウント先に選ぶ。

ゲームを前回と同じ **GAME PAUSE**、左側が下の向きにし、iSHへ戻る。次を実行するとフォルダ選択が開く。

```sh
mkdir -p /mnt/necro_p15
mount -t ios . /mnt/necro_p15
```

選択後、次の1行で開始する。

```sh
cd /mnt/necro_p15 && sh test_010.sh
```

P1.5表示、継続用プロセス開始、ゲーム起動要求の順に出る。ゲームへ切り替わったらそのまま約45秒待ち、iSHへ戻る。ポーズ解除・移動・リスタート・購入はしない。停止はiSHでCtrl+C。

一時継続処理はTEST-006/007と同じ`/dev/location`読取りを使用し、値は`/dev/null`へ捨てる。保存・送信はしない。終了時は所有PIDへ停止要求するが、停止完了を検証した意味ではない。資料の保存後にiSHをアプリスイッチャーから終了する。

## 判定の範囲

今回合格にできるのは、実ゲームのポーズ画像が取得元から横長・正しい比率・原バイトで返り、各条件の時間を測れたことまで。TEST-007のnative_i386測定と件数/形式/画像サイズ/復号方式を揃えて比較する。capture_to_inspectedは従来の画素検査終了までで、新メタデータ照合の時間は含まない。新照合・保存も含むtrial_totalと全体時間も併記する。

人より速いという要件は未達成扱いを維持する。画像取得だけでなく、認識、入力、画面反映、毎分の商品確認完了回数の実機結果で判断する。入力座標・画像鮮度・取消・長時間周回は今回の静止ポーズ取得では合格にしない。

### TEST-007との時間比較

単位ms。各形式4回、ウォームアップ除外なし。p95はnearest-rankのため、この件数では最大値。比較元もnative_i386・12回・ゲームポーズだが画像の寸法・圧縮バイト・表示内容が異なり、別実行である。

| 形式 | TEST-007 取得→検査 中央値 | TEST-010 同中央値 | TEST-010 同p95 | TEST-010 trial_total中央値 |
| --- | ---: | ---: | ---: | ---: |

| JPEG scale2 | 840.267 | 922.941 | 964.696 | 1182.548 |

観測上は中央値が約7.1%、9.8%、9.1%増えた。横長化の処理自体による増分とは分離できない。受信後の回転・縦横リサイズ・再符号化は追加していない。画像取得だけで0.44〜0.92秒程度という結果から、人より速い周回や暫定150ms/10Hzの観測条件を達成したとは判断しない。診断ファイル書込み・起動待ちも含む全体時間の逆数を画像FPSにはしない。

### 鮮度と合格の限界

3枚の操作バナーの時間表示は0:02/0:03/0:05と変化しているが、ゲーム本体の新鮮さや150ms以内の遅延を示さない。形式ごとに4/7/10、5/8/11、6/9/12のSHAが反復する。`same_bytes_as_previous=false`は直前の異形式画像との比較であり、同形式の新しい画面を証明しない。capture_time_ns/source_sequence/frame_ageは全て未測定。残り9回はメタデータとハッシュを確認した範囲であり、原画像を目視したとは扱わない。

今回閉じるのは「取得元の横長原画像と表示比率」の修正。入力座標、鮮度、入力の期限/取消、続行E2E、速度・耐久は未合格。次は取得元の入力経路・期限契約を整備し、推測座標を送らず限定1回の続行試験へ進む。自動探索/購入は追加しない。

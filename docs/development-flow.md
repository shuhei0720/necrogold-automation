正本: ユーザー指定 [AI-Driven-Development Codex版](https://github.com/shuhei0720/AI-Driven-Development/blob/3cf01c46395e83696ba8900e429297ff5f249e2f/AI-Driven-Development-CAF-ALZ-Codex.md)。参照commit `3cf01c46395e83696ba8900e429297ff5f249e2f`、blob `646fc7225c3b08d4073b59a4d862b3f52294b800`。Azure構築例そのものは移植せず、要件分離・context管理・TDD・独立レビューを適用する。

## 最新の運用方針（2026-11-10 日本時間）

ユーザーの最新指示を優先し、品質を維持したまま検証範囲・レビュー・CIの実行頻度を変更する。作業時間に固定上限や20〜30分という目標を設けない。必要な調査・修正・確認には時間を使い、長引く場合は理由、確認済みの事実、未解明点、残作業を報告する。時間内に収めるための品質低下を認めない。

通常の実機反復は、受領ZIPで停止理由を確認→原因/変更範囲/期待値/検査項目の短い計画→変更箇所の単体と関連回帰→独立した差分レビュー1回→必要なビルド/配布物確認→実機、とする。画像認識は実画像、制御は記録された時刻・状態を根拠にし、再現できない範囲を明示する。未収録の未来画像や実応答を合成して実機再現と呼ばない。

| 対象 | 選び方 |
| --- | --- |
| 単体・関連回帰 | 変更した処理と失敗箇所を毎回確認。既存のassert・拒否条件を維持する |
| 結合・並行処理 | 通信、取得、入力、取消、queue間の受渡し等を変更した場合に、その境界を確認する |
| フルCI・大規模合成試験 | 商品到達が安定した節目、大きな契約/構造変更、広い影響や未解決リスクの具体的根拠がある場合に実施。通常修正の既定経路にしない |
| IPA・配布物 | native変更時に必要なビルドとseal/来歴/実compiler/配布物/source同一性確認を行う。client/資料だけの変更で不要なIPA更新を求めない |
| レビュー | 通常は独立した差分レビュー1回。大きな変更のみ下記8工程の重点レビューを適用する |

各変更で選んだ検査と、選ばなかった検査の理由・前回結果を再利用できる根拠を記録する。未実施・古い結果を最新成功とは書かない。合成試験は保証範囲内の補助とし、実機の代用にしない。安全契約、商品/候補保持、毎拍歩行、人より速い処理の要件を落とさない。

主指標は実機の商品確認までの到達率。0歩/移動/開扉/入店/商品確認を区別し、途中の歩数増加や試験件数だけを成功にしない。関係のないリファクタリング・試験基盤の修理を同じ修正へ混ぜない。必要になった場合は原因とscopeを明示する。

既存workflowがフル実行しか提供していない場合、通常修正のために機械的に起動せず、必要な検査とIPA作成だけの経路を整備する。未整備の短いCI経路を運用済みとは書かない。今回の方針記録と受領ログ解析だけではCIやIPA作成を開始しない。

## Xを必要最低限十分にする

入力はプロンプト、ルール、コード、文書、スキル、外部情報、対話履歴から成る。通常は [AGENTS](../AGENTS.md)・[最新状態](status.md)・[索引](context.md) から始め、今回必要な正本/関数/試験だけを選ぶ。要件は [正本](requirements/necrogold.md)、実装順と方法は今回の計画（通常修正は短い計画、大きな契約・構造変更は8項目計画）へ置く。版ごとの結果は台帳に集約し、毎回の読込へ複製しない。

## 大きな契約・構造変更の8工程

| 工程 | 成果物・条件 |
| --- | --- |
| 1. 計画 | 概要・背景・詳細設計・テスト影響範囲・新規テストケース・実装順・コミット前テスト・スコープ外の8項目。既知事項を聞き直さない |
| 2. プラン相互レビュー | 作成経緯を渡さないfreshな設計・網羅/異常系・安全/運用の独立担当が正本と計画を確認 |
| 3. 網羅レビュー | 正常・境界・異常・要件外を期待値と対応。人間も期待値を確認できる記録を残す |
| 4. 実装 | 計画順に進め、計画外の大きな変更は計画へ反映。未解決は明示 |
| 5. テスト | 機能ごとに実装前のassertion Red→最小Green→Refactor。compile/環境不足はRedではない。機能実装後だけのテストにしない |
| 6. 実装相互レビュー | 別担当の設計・網羅・安全レビュー。修正込み最大3周、P0を解消し残P1/P2の理由・次工程を記録 |
| 7. 人間レビュー | データの流れ・判断・代替案・証拠・未検証・実機結果を提示。実ゲームでの成立を確認 |
| 8. リファクタリング | Greenを確認し、責務/重複/入力contextを整理。仕様変更を混ぜず、変更ごとに影響のある検査を行う |

試験期待の削除・skip・常時成功mockでGreenを作らない。挙動不変の文書整理では、既存Greenとコードbytes不変、参照・移送・読込量の検査を対応させる。実機の既知不合格がこのGreenで解消したとは扱わない。

## 証拠と権限

単体・合成結合・録画再生・実ゲームE2E・iPhone受入を分ける。機械上の成功だけでユーザーの全要件を達成としない。レビューには対象commit・期待値の根拠・実行結果・未確認を残し、通常修正へ3担当/複数周を形式的に要求せず、大きな変更でも前incrementの閉じたレビューを新scopeの第4周として再開しない。[詳細規則](rules/review.md)。

ユーザーはGitHubへのコード/資料保存と開発継続を承認済み。保存だけの追加承認は求めない。原文のPR投稿前承認は実際にPRを作る段階へ適用する。

過去各版での工程適用は [元flow全文](archive/context-pre-refactor/README.md) と [実機台帳](device-tests/README.md) に保存した。現在の工程は [最新状態](status.md) と今回の計画で判断する。

正本: ユーザー指定 [AI-Driven-Development Codex版](https://github.com/shuhei0720/AI-Driven-Development/blob/3cf01c46395e83696ba8900e429297ff5f249e2f/AI-Driven-Development-CAF-ALZ-Codex.md)。参照commit `3cf01c46395e83696ba8900e429297ff5f249e2f`、blob `646fc7225c3b08d4073b59a4d862b3f52294b800`。Azure構築例そのものは移植せず、要件分離・context管理・TDD・独立レビューを適用する。

## Xを必要最低限十分にする

入力はプロンプト、ルール、コード、文書、スキル、外部情報、対話履歴から成る。通常は [AGENTS](../AGENTS.md)・[最新状態](status.md)・[索引](context.md) から始め、今回必要な正本/関数/試験だけを選ぶ。要件は [正本](requirements/necrogold.md)、実装順と方法は今回の8項目計画へ置く。版ごとの結果は台帳に集約し、毎回の読込へ複製しない。

## 8工程

| 工程 | 成果物・条件 |
| --- | --- |
| 1. 計画 | 概要・背景・詳細設計・テスト影響範囲・新規テストケース・実装順・コミット前テスト・スコープ外の8項目。既知事項を聞き直さない |
| 2. プラン相互レビュー | 作成経緯を渡さないfreshな設計・網羅/異常系・安全/運用の独立担当が正本と計画を確認 |
| 3. 網羅レビュー | 正常・境界・異常・要件外を期待値と対応。人間も期待値を確認できる記録を残す |
| 4. 実装 | 計画順に進め、計画外の大きな変更は計画へ反映。未解決は明示 |
| 5. テスト | 機能ごとに実装前のassertion Red→最小Green→Refactor。compile/環境不足はRedではない。機能実装後だけのテストにしない |
| 6. 実装相互レビュー | 別担当の設計・網羅・安全レビュー。修正込み最大3周、P0を解消し残P1/P2の理由・次工程を記録 |
| 7. 人間レビュー | データの流れ・判断・代替案・証拠・未検証・実機結果を提示。実ゲームでの成立を確認 |
| 8. リファクタリング | Greenを確認し、責務/重複/入力contextを整理。仕様変更を混ぜず、変更ごとに影響のある検査を行う |

試験期待の削除・skip・常時成功mockでGreenを作らない。挙動不変の文書整理では、既存Greenとコードbytes不変、参照・移送・読込量の検査を対応させる。実機の既知不合格がこのGreenで解消したとは扱わない。

## 証拠と権限

単体・合成結合・録画再生・実ゲームE2E・iPhone受入を分ける。機械上の成功だけでユーザーの全要件を達成としない。レビューには対象commit・期待値の根拠・実行結果・未確認を残し、前incrementの閉じたレビューを新scopeの第4周として再開しない。[詳細規則](rules/review.md)。

ユーザーはGitHubへのコード/資料保存と開発継続を承認済み。保存だけの追加承認は求めない。原文のPR投稿前承認は実際にPRを作る段階へ適用する。

過去各版での工程適用は [元flow全文](archive/context-pre-refactor/README.md) と [実機台帳](device-tests/README.md) に保存した。現在の工程は [最新状態](status.md) と今回の計画で判断する。

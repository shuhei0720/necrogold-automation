# 採用するAI駆動開発フロー

ユーザー指定の [AI-Driven-Development Codex版](https://github.com/shuhei0720/AI-Driven-Development/blob/3cf01c46395e83696ba8900e429297ff5f249e2f/AI-Driven-Development-CAF-ALZ-Codex.md) を確認しました。

参照commit: `3cf01c46395e83696ba8900e429297ff5f249e2f`、文書blob: `646fc7225c3b08d4073b59a4d862b3f52294b800`。2026-11-05（日本時間）確認。

Azure/ALZの構築例そのものを移植するのではなく、要件分離、コンテキスト管理、TDD、独立レビュー、8ステップを適用します。

| 原文の工程 | このプロジェクトでの成果物・条件 |
| --- | --- |
| 事前準備: 要件とルール | `requirements/necrogold.md`、`AGENTS.md`、`rules/`。何を・なぜ・合格条件を要件に置く |
| 1. インタビュー式のプラン | `plans/rebuild.md`。概要・背景・詳細設計・テスト影響範囲・新規テストケース・実装順・コミット前テスト・スコープ外の8項目 |
| 2. プランのAI相互レビュー | 設計、異常系・運用、セキュリティを独立担当でレビュー。作成経緯を渡さず資料・差分・基準を渡す |
| 3. テスト網羅レビュー | 受け入れ条件とテストを対応。境界・異常・スコープ外の混入を確認。期待値は人間もレビューする |
| 4. 実装 | プランの順序・担当に従う。計画外の大きな変更はプランへ反映し、未解決なら報告 |
| 5. テスト実装と全通過 | 4と分離して後付けせず、機能ごとに先にRedを観測→最小Green→Refactor。実機試験はモックで代用しない |
| 6. 実装のAI相互レビュー | 別担当が設計・境界・セキュリティ・ルールを確認。修正を含め最大3周 |
| 7. 人間のレビュー | データの流れ、設計判断、代替案、根拠、実機結果と未検証事項を説明する |
| 8. テスト駆動リファクタリング | Greenを確認してから責務分割・重複整理。仕様変更を混ぜない |

原文には工程4の後に工程5が並びますが、同じ原文のTDD節が要求する「実装前に失敗を確認」を守り、実装とテストは1ケースずつ繰り返します。

## 今回の到達点

要件・プラン・動画事例・旧版ソースを保存し、プランの独立レビューとテスト網羅レビューを2周行いました。残るP2の計測内訳も資料へ反映しました。ゲーム操作プログラムの新規実装、CIでのアプリ試験、実機試験はまだ行っていません。旧版の保存は配布ではありません。

速度の暫定値、金壁への接近上限、対象アイテム正例はプランに未確定箇所を明示します。既に答えのある向き・操作設定・最重要要件を再質問しません。実機のバージョンや取得能力は小さな計測で取得して決めます。

原文のPR投稿前承認はPRを作る段階に適用します。今回のリポジトリ作成と既存コード・資料の保存は、ユーザーから既に依頼されています。保存だけを理由に追加の承認を求めません。
